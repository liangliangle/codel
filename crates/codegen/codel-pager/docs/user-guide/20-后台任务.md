# 后台任务与监控 (Background Tasks and Monitoring)

Codel 在不阻塞对话的情况下运行长生命周期的进程。本文档涵盖后台命令、`/loop` 命令、`monitor` 工具和调度器。

---

## 后台命令

在 `run_terminal_command` 工具上设置 `background: true` 以在后台运行命令。它会立即返回一个任务 ID；可以通过 `get_command_or_subagent_output` 获取输出。

### 工作原理

1. 智使 (Agent) 使用 `background: true` 调用 `run_terminal_command`。
2. 命令开始在后台运行。
3. 智使收到一个 `task_id` 供后续引用。
4. 当命令完成时，对话中会出现一条通知。

### 获取输出

使用 `get_command_or_subagent_output` 工具检查后台命令或分身智使 (subagent)：

- `get_command_or_subagent_output(task_id)` — 获取当前输出和状态而不等待
- `get_command_or_subagent_output(task_id, timeout_ms=30000)` — 等待指定的毫秒数直到其完成

### 等待多个任务

使用 `wait_commands_or_subagents` 一次阻塞等待多个任务：

- `task_ids` — 要等待的任务 ID 列表（最多 20 个）
- `mode` — `wait_any` 在第一个任务完成时返回；`wait_all` 等待每一个任务
- `timeout_ms` — 最大等待时间，以毫秒为单位（默认：30 秒）

该工具返回您列出的每个任务的状态和输出。

### 终止后台任务

使用 `kill_command_or_subagent(task_id)` 终止运行中的后台任务或分身智使。该工具会向 shell 进程发送 SIGTERM，接着发送 SIGKILL，并向分身智使发送取消 (Cancel) 和关闭 (Shutdown) 信号。如果任务已被终止或已经退出，它会报告成功。

### 常见用例

- **开发服务器**: 在后台启动开发服务器并继续编码
- **测试套件**: 在后台运行测试同时处理修复
- **构建进程**: 开始构建并在稍后检查结果
- **耗时较长的编译**: 开始编译并继续进行其他任务

## 将正在运行的任务发送至后台

在交互式 TUI 中，按 `Ctrl+B` 将正在运行的前台命令发送至后台。这是唯一的后台化快捷键。在以下情况执行此操作：

- 命令耗时超出预期。
- 您想在命令运行期间向智使询问其他问题。
- 您在进程启动后意识到它需要运行很长时间。

任务将继续运行，并且您会在其完成时收到通知。

## /loop 命令

`/loop` 在重复的间隔内运行一个提示词。它适用于轮询任务、定期检查和持续监控。

### 语法

```
/loop [interval] <prompt>
```

时间间隔格式支持：

| 格式 | 示例 | 描述        |
| ------ | ------- | ------------------ |
| `Ns`   | `60s`   | 每 N 秒（最少 60 秒） |
| `Nm`   | `5m`    | 每 N 分钟    |
| `Nh`   | `2h`    | 每 N 小时      |
| `Nd`   | `1d`    | 每 N 天       |

### 示例

```
/loop 5m 检查测试套件是否通过并报告任何失败
/loop 2h 总结自上次检查以来的新提交
/loop 60s 检查 localhost:3000 的开发服务器是否有响应
```

### 行为

- 提示词会在创建时立即触发，然后以指定间隔重复
- 每次触发都会开启智使的新一轮交互
- 重复任务在 7 天后自动过期
- 最多可同时激活 50 个定时任务

## monitor 工具

`monitor` 工具用来从长时间运行的脚本中传输事件流。输出的每一行都将作为对话中的通知。`monitor` 工具是 `/loop` 的流式处理对应物：`/loop` 用于定期检查，而 `monitor` 用于实时事件流。

### 工作原理

1. 您提供一个 shell 命令 (`command`) 和一个简短的描述 (`description`)，该描述会出现在每个通知中。
2. Codel 会将命令的标准输出 (stdout) 和标准错误 (stderr) 合并到一个单一的输出文件中。
3. 该文件中的每一行新内容都会作为通知传递到对话中。
4. monitor 会一直运行直到命令退出或您将其停止。

### 脚本编写指南

- **始终在管道中使用 `grep --line-buffered`。** 如果没有它，管道缓冲可能会将事件延迟几分钟。
- **在轮询循环中处理短暂故障** (`curl ... || true`)。一次失败的请求不应导致 monitor 停止。
- **使用选择性过滤器。** 每一行都会成为一条消息，因此切勿直接通过管道传输原始日志。
- **设置与源匹配的轮询间隔。** 对于远程 API，请使用 30 秒或更长时间以遵守速率限制；对于本地检查，请使用 0.5 到 1 秒。
- **标准输出和标准错误都会生成事件。** 重定向您不希望作为事件的输出——例如，追加 `2>/dev/null`——或将其过滤掉。

### 示例

```bash
# 观察日志文件中的错误
tail -f /var/log/app.log | grep --line-buffered "ERROR"

# 监控目录中文件变化
inotifywait -m --format '%e %f' /watched/dir

# 轮询 GitHub 以获取新的 PR 评论
last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
while true; do
  now=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  gh api "repos/owner/repo/issues/123/comments?since=$last" \
    --jq '.[] | "\(.user.login): \(.body)"'
  last=$now; sleep 30
done
```

### 持久监控器

如果希望监控器在会话的整个生命周期中运行，请设置 `persistent: true`：

- PR 监控
- 日志追踪
- CI 状态监控

使用 `kill_command_or_subagent(task_id)` 停止持久监控器。

### 音量控制

如果 monitor 产生过多的事件，Codel 将自动停止它。发生这种情况时，请使用更严格的过滤器重新启动 monitor。优先使用 `grep --line-buffered`、`awk` 或一个仅发出您关心的事件的包装脚本。

## 调度器 (The Scheduler)

调度器提供了用于创建重复任务的底层 API。`/loop` 只是围绕该调度器的便捷封装。

### scheduler_create

创建一个定时任务：

| 参数        | 描述                                              |
| ---------------- | -------------------------------------------------------- |
| `interval`       | 运行频率：`"5m"`, `"2h"`, `"1d"`, `"60s"`       |
| `prompt`         | 每次触发时要执行的提示词                  |
| `fire_immediately`| 是否在创建时以及时间间隔之外立即触发（默认：`false`） |
| `recurring`      | 是否重复运行（默认：`true`）或仅触发一次（`false`）          |
| `durable`        | 是否跨会话持久化（默认：`false`）               |

### scheduler_list

列出所有活动的定时任务及其 ID、提示词、时间间隔和下一次触发时间。

### scheduler_delete

按 ID 取消定时任务。如果找到任务并删除，则返回成功。

## 任务面板 (The Tasks Pane)

在交互式 TUI 中，按 `Ctrl+G` 切换任务面板。该面板在单个视图中列出：

- 运行中的分身智使及其进度
- 活跃的后台任务及其状态
- monitor 和 `/loop` 任务，各带有一个实时行数徽章
- 每个条目的任务 ID

要切换到提示词队列面板，请按 `Ctrl+;`。

## 后台运行状态行

每当后台有任务仍在运行而智使看起来处于空闲状态时（在两轮交互之间，或者当交互处于用户可中断的等待时），提示框上方会出现一个持续的状态行：

```
◎ 1 command · 2 monitors · 1 loop · 1 subagent still running
```

它会统计运行中的后台命令、monitors、已调度的 `/loop` 任务和后台分身智使，并随着它们各自的完成而实时更新。它们中的任何一个都可能唤醒智使以开始新的一轮交互（命令和分身智使在完成时，monitors 在事件触发时，loops 在其定时器触发时），因此这个提示会一直保留直到没有任务剩下为止。这些正在运行的计数仅存在于此状态行中：任务完成时会在对话文本中记录为单个 "Task completed"（任务完成）标签，而 "Worked for"（已工作）标记则保持不变——对话记录永远不会重复或重述这些运行的计数。

## 用例和模式

### 开发服务器 + 编码

在后台启动开发服务器并继续编写代码：

```
Start the dev server with `npm run dev` in the background, then implement the login form.
```

智使使用 `background: true` 运行开发服务器并继续编写代码。当服务器启动时，您会看到一条通知。

### 持续测试监控

```
/loop 5m 运行测试套件并报告自上次运行以来的任何新失败
```

每 5 分钟，智使会运行一次测试，并仅报告新的失败情况。

### 日志监控

使用 `monitor` 监听特定事件：

```
监控应用日志中的 ERROR 和 WARN 条目。使用：
tail -f /var/log/app.log | grep --line-buffered -E "ERROR|WARN"
```

每个错误或警告都会作为对话中的一条通知出现。

### CI 流水线监控

```
/loop 2m 检查此 PR 的 GitHub Actions 运行状态。完成后请报告。
```

## 最佳实践

- **使用 `background` 来执行一次性长时间命令**（构建、测试套件、服务器启动）
- **使用 `/loop` 进行定期检查**（CI 状态、测试运行、健康检查）
- **使用 `monitor` 获取实时事件流**（日志追踪、文件监控）
- **将 `scheduler_create` 与 `recurring: false` 结合使用**以执行延迟的一次性任务
- **保持 monitor 过滤器精简** —— 首选 `grep --line-buffered` 而不是原始日志流
- **不要在普通命令中使用 sleep 循环** 来进行轮询 —— 改为使用带有 `timeout_ms` 的 `get_command_or_subagent_output`
- **设置合理的轮询间隔** —— 对于远程 API 请设为 30 秒以上以避免速率限制，本地检查可更短
