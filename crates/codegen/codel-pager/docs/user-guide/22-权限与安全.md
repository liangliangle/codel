# 权限与安全

Codel 可以读取文件、搜索代码、编辑文件以及运行 Shell 命令。权限系统负责控制智使（Agent）被允许执行的操作。您可以组合使用多个独立的防御层：权限规则、权限模式、钩子（Hooks）以及操作系统级别的沙盒安全环境（Sandbox）。

本指南将说明工具调用是如何获得授权的，如何通过命令行界面（CLI）、原生配置或 Claude 设置来配置权限规则，以及如何使用在所有模式下均适用的 `PreToolUse` 钩子来实现白名单。

---

## 工具调用如何获得授权

当模型请求使用工具时，系统会按顺序进行以下检查：

1. **`PreToolUse` 钩子**。钩子可以在任何其他检查之前拒绝工具调用。允许调用的钩子并不会跳过后续检查；它仅仅是表示不拒绝。参见 [10-hooks.md](10-hooks.md)。

2. **权限规则**（来自配置文件或 `--allow`/`--deny` 标志）
   - 匹配到的 `deny` 规则会拒绝调用。`deny` 的优先级高于其他所有规则。
   - 匹配到的 `ask` 规则会向您进行询问提示，包括针对原本会自动批准的文件读取、搜索和 Shell 命令。
   - 匹配到的 `allow` 规则会批准调用。

3. **被记住的授权**。您在先前的提示中保存的针对每个命令的批准将在此处应用，其作用域限定在当前项目中。现有的授权可以满足 `ask` 规则，而无需重新提示。[危险命令列表](#危险命令)中的命令会再次提示，而不会使用被记住的前缀。参见[交互式批准](#交互式批准及其持久化位置)。

4. **内置的自动批准**。只读工具和一组固定的只读 Shell 命令在运行时无需提示（见下文）。

5. **提示策略**（由[权限模式](#权限模式)设定）：提示您、自动批准或自动拒绝调用。

总是批准模式（`bypassPermissions`）在第 2 步之后短路此流水线：匹配 Shell 命令片段的 `deny` 规则、钩子和 `ask` 规则仍然适用，但不查询被记住的授权（包括被记住的“永不批准”条目），且对非 Shell 工具的 `ask` 规则也不会进行提示。

## 默认永远不提示的操作

在所有模式（包括 `dontAsk`）下，除非匹配的 `deny` 规则或钩子阻止了它们，以下操作被视为只读，并且运行时不会提示。`ask` 规则会强制对文件读取、搜索和 Shell 命令进行提示（参见[工具调用如何获得授权](#工具调用如何获得授权)）。

### 只读工具

- `read_file`
- `list_dir`
- `grep` (内容搜索)
- `web_search`
- `todo_write`
- `get_command_or_subagent_output` / `wait_commands_or_subagents` / `kill_command_or_subagent` (分身智使控制)
- 技能调用

### 只读 Shell 命令

在拆分链式命令（在 `&&`, `||`, `;` 和管道符上）之后，当以下命令作为主命令出现时，它们会被识别为只读命令。此列表基于单词边界进行匹配，因此 `ls` 不会匹配 `lsof` 或 `less`。（您自己的 `Bash(...)` 规则的匹配方式不同；参见[规则匹配参考](#规则匹配参考)）。

**文件系统（只读查看）：**
- `ls`, `cat`, `pwd`, `date`, `whoami`, `hostname`, `uptime`, `ps`
- `head`, `tail`, `wc`, `sort`, `uniq`, `tr`, `cut`

**Git（只读）：**
- `git status`, `git branch`, `git log`, `git diff`, `git ls-files`, `git show`, `git rev-parse`

**搜索与检查：**
- `grep`, `rg`（不是 `rg --pre` / `rg --pre=…`，因为它们会为每个文件生成预处理器）

**Kubernetes（只读）：**
- `kubectl get`, `kubectl logs`, `kubectl describe`

> **注意：** `tee` 不在此列表中，因为它可以将输入写入任意文件。`cargo check` 不在此列表中，因为它会编译并运行 `build.rs`、过程宏以及仓库中的任何 `build.rustc-wrapper`（因此在询问模式下它会提示；自动审查模式下仍然可能通过启发式策略将 `cargo` 作为项目代码运行器予以允许）。`sort --compress-program=…`（包含唯一长选项缩写）、`git -c` / `--config-env` 覆盖、以及其本地/工作树配置会安装可执行钩子（`core.fsmonitor`、`diff.*.command`/`textconv`/`external` 驱动，或 Shell `alias.<safe-subcommand> = !…`）的 git 命令，将会提高请求级别并引发提示，而不是自动批准，除非用户授予了完全匹配的脚本或开启了 YOLO 模式。

这些检查针对每个命令片段进行。在像 `ls && rm -rf /` 这样的命令中，`ls` 片段被识别为只读，但 `rm` 片段不在列表中。在 `default` 模式下，对 `rm` 片段会进行提示；在 `dontAsk` 模式下它会被拒绝。

## 权限模式

提示策略被命名为以下模式之一：

| 模式                | 行为                                                                 | 典型用途                        |
|---------------------|--------------------------------------------------------------------------|---------------------------------|
| `default`           | 对任何未预先批准的操作进行提示                                           | 日常交互使用                    |
| `dontAsk`           | 拒绝任何没有显式 allow 规则或内置自动批准的操作                          | 无头交互模式、CI、高安全性环境  |
| `bypassPermissions` | 自动批准工具调用（`deny` 规则、钩子和 Shell `ask` 规则仍旧适用）         | 受信任的环境                    |
| `acceptEdits`       | 自动批准文件编辑（`search_replace`, `write` 等）                         | “接受编辑”的工作流              |
| `plan`              | 为了兼容性而接受；筹划会话是一个单独的功能（参见 [19-筹划模式.md](19-筹划模式.md)） | 结构化筹划会话                  |

### 设置模式

可以通过 `.claude/settings.json` 中的 `defaultMode` 来设置模式（参见 [Claude Code 兼容性](#3-claude-code-兼容性-claudesettingsjson)）。`dontAsk`、`acceptEdits` 和 `bypassPermissions` 会改变其提示策略；`default` 和 `plan` 会保持标准提示行为。

命令行标志 `--permission-mode` 应用于 `bypassPermissions`（总是批准）和 `default`；显式标志值始终覆盖配置中的模式设置。如果在标志中传递 `dontAsk`、`acceptEdits` 或 `plan` 能够被接受但不会启用该策略；请通过 `defaultMode` 进行设置。

在无头交互模式运行（`-p`）中，会导致提示的工具调用将被取消并报告给模型，而不是等待输入。如果要在自动化中默认拒绝，请设置 `defaultMode: "dontAsk"`。

### 禁用总是批准模式

管理员可以关闭总是批准（`bypassPermissions` / `--always-approve`），以防止从命令行界面、TUI 切换器或 `/always-approve` 命令中启用它。在 `requirements.toml` 中设置专属的键：

```toml
[ui]
disable_bypass_permissions_mode = true   # 默认: false。true = 锁定关闭。
```

不要将 `permission_mode` 用于此目的；这是一个可由用户切换的默认值，而不是锁。旧的 `[ui] yolo = false` 键在 `requirements.toml` 中也会为了向后兼容性而禁用该模式；在 `config.toml` 中，同样的键仍是一个可切换的首选项。

用户级别的 `~/.codel/requirements.toml` 处于用户的控制之下，所以开发者可以通过编辑该文件来移除锁定。如果需要强制用户不可覆盖，请将设置部署到拥有 root 权限的系统文件 `/etc/codel/requirements.toml` 中。

> **注意：** Codel 会遵守 Claude Code 的 `managed-settings.json` 中的权限规则，但不会遵守它的 `disableBypassPermissionsMode` 锁定。要在 Codel 中禁用总是批准，请使用如上所示的 `requirements.toml`。

## 配置权限

Codel 从三个兼容的来源读取权限规则。所有来源的规则将被合并为一个集合；一条规则的作用取决于其动作（`deny` > `ask` > `allow`），而不是它来源于哪个文件。

### 权限规则存放的位置（作用域）

权限规则可以是全局的（所有项目）、项目作用域的（单个仓库），或项目中对您个人的：

| 作用域 | 文件 | 是否与团队成员共享 |
|-------|------|-----------------------|
| 全局（所有项目） | `~/.codel/config.toml` | 否 |
| 项目（已提交） | `<project>/.codel/config.toml` | 是（提交它） |
| 项目（个人） | `<project>/.claude/settings.local.json` | 否（将其添加到 gitignore） |
| 交互式授权 | 由 Codel 内部存储，针对每个项目 | 否 |

关于作用域的说明：

- Codel 会从仓库根目录向下一直到您的工作目录，发现每一层级的 `.codel/config.toml`，因此子目录可以在仓库根目录之上添加规则。
- 所有的作用域的规则被合并为一个规则集；`deny` > `ask` > `allow` 跨越了作用域，因此不能通过项目的 `allow` 来覆盖全局的 `deny`。
- Codel 没有原生的 `config.local.toml`。对于项目中的个人或未提交的规则，请使用 `.claude/settings.local.json`；Codel 会直接读取它（参见 [Claude Code 兼容性](#3-claude-code-兼容性-claudesettingsjson)）。
- 交互式的“总是允许”决策存储在仓库外部，其作用域限定在项目内（参见[交互式批准及其持久化位置](#交互式批准及其持久化位置)）。

要停止一个项目中特定命令的提示，可以在该项目的 `.codel/config.toml`（或 `.claude/settings.json`）中添加一条更窄的 allow 规则：

```toml
[permission]
allow = ["Bash(cargo test *)", "Bash(npm run build)"]
```

这只会批准列出的命令。相比之下，总是批准模式会批准所有的工具调用。

### 1. 命令行标志

```bash
codel -p "Review the API changes" \
  --allow 'Bash(git *)' \
  --allow 'Bash(gh *)' \
  --allow 'Read' \
  --allow 'Grep' \
  --deny 'Bash(rm -rf *)'
```

`--allow RULE` 和 `--deny RULE` 可以重复使用，并始终强制执行。

规则语法示例：
- `Bash(git *)` — 任何以 `git ` 开头的命令
- `Bash(npm run build)` — 完全匹配的命令（或前缀）
- `Bash(git commit:*)` — 带有 `cmd:*` 后缀形式，相当于针对 `git commit` 的前缀匹配
- `Read(src/**)` — 在 `src/` 下的读取权限
- `Edit(**/*.rs)` — 编辑任何 Rust 文件
- `Grep` — 所有 grep 操作
- `MCPTool(my-server__*)` — 来自特定服务器的 MCP 工具

查阅[规则匹配参考](#规则匹配参考)了解确切的匹配语义，包括链式命令和通配符是如何被评估的。

### 2. 原生配置 (`~/.codel/config.toml` 和 `.codel/config.toml`)

```toml
[permission]
rules = [
  { action = "allow", tool = "bash", pattern = "git *" },
  { action = "allow", tool = "bash", pattern = "gh *" },
  { action = "allow", tool = "read" },
  { action = "allow", tool = "grep" },
  { action = "deny",  tool = "bash", pattern = "rm -rf *" },  # 阻止危险的模式
  { action = "ask",   tool = "edit" },
]
```

结构化的 `tool` 字段接受小写的名称 `bash`, `read`, `edit`, `grep`, `mcp`, `webfetch` 和 `websearch`，它们对应于 [工具名称](#工具名称) 中的工具类。

由于 `deny` 总是生效，所以你无法将这些 `allow` 规则与 `bash` 的一条拦截一切的 `deny` 结合使用来表示“只允许 git/gh”；因为 `deny tool = "bash"` 规则同样会阻止 `git` 和 `gh`。如果想默认拒绝，请在 `.claude/settings.json` 中使用 `defaultMode: "dontAsk"` 或者使用 `PreToolUse` 钩子（见下文）。

来自全局的 `~/.codel/config.toml` 和每个项目的 `.codel/config.toml`（从仓库根目录一直到你的工作目录）的规则会同任何 `.claude/settings.json` 的规则一起被合并到一个规则集中。

您所在组织部署的托管配置也提供了 `[permission]` 规则：系统 `/etc/codel/managed_config.toml` 以及由 Codel 自动维护的用户级副本 `~/.codel/managed_config.toml`。托管规则与来自任何其他来源的规则进行合并，其中特定于托管 `allow` 规则的两个属性：你自己的 `deny` 和 `ask` 规则优先级高于托管的 `allow`（严重性排序），并且在关闭总是批准锁定状态时，会忽略包罗万象的托管 `allow`。对于用户无法通过编辑去除的规则，请使用具备 root 权限的系统文件 `/etc/codel/requirements.toml`。

在会话启动时，来自每个来源的权限规则被一次性读取。任何更改将在下一次会话中生效。

原生的 `[permission]` 部分还接受使用类似于 `--allow` / `--deny` 标志和 `.claude/settings.json` 中使用的字符串规则，采用紧凑的 `allow` / `deny` / `ask` 字符串数组形式：

```toml
[permission]
deny = [
  "Read(/Users/you/private/**)",
  "Edit(/Users/you/private/**)",
  "Bash(rm -rf *)",
]
allow = [
  "Bash(git *)",
  "Bash(gh *)",
]
```

`deny` 的优先级总是高于 `allow`（评估顺序为 `deny` > `ask` > `allow`），无论是哪种顺序或来源。如果要阻止对你项目之外的路径在 OS 级别也被读取，请将 deny 规则与 `strict` 沙盒安全环境配置相组合（参见 [18-沙盒安全环境.md](18-沙盒安全环境.md)）。

### 3. Claude Code 兼容性 (`.claude/settings.json`)

Codel 会读取 `~/.claude/settings.json` 和 `~/.claude/settings.local.json`，以及项目级别的 `<project>/.claude/settings.json` 和 `settings.local.json`（直到仓库根目录）。用于权限规则的原生 `.codel` 来源是 `config.toml`，如上一节所述。

示例：

```json
{
  "permissions": {
    "defaultMode": "dontAsk",
    "allow": [
      "Read",
      "Grep",
      "Bash(git *)",
      "Bash(gh *)"
    ],
    "deny": [
      "Bash(rm -rf *)"
    ]
  }
}
```

支持的 `defaultMode` 值包括 `default`、`acceptEdits`、`bypassPermissions`、`dontAsk` 和 `plan`。Codel 会从其权威的位置（即 `permissions` 下）读取 `defaultMode`；当嵌套键不存在时，系统也会接受顶层的 `defaultMode`。

`permissions.allow`、`permissions.deny` 和 `permissions.ask` 条目会被转换为原生的规则，然后按照 [规则匹配参考](#规则匹配参考) 中的语义进行匹配。翻译说明：

- 有关 MCP 工具的规则必须使用 `MCPTool(server__tool)` 形式；`mcp__server__tool` 形式永远不会匹配（参见 [MCP 规则](#mcp-规则)）。
- 包含无法识别的工具名称的规则，以及诸如 `Agent(model:opus)` 这样的参数规则将被跳过并发出警告，而不是加载失败。
- `permissions.additionalDirectories` 会被解析但不被支持。

您可以通过按 **Ctrl+I** （“导入 Claude 设置”）交互式地导入现有的 Claude 设置。

## 规则匹配参考

本节明确定义了规则是如何被匹配的。

### Bash 规则

一个 `Bash(...)` 模式通过以下两种方式之一匹配一条命令：

- **前缀**：该命令以模式文本开头，并且逐字符匹配。由于没有单词边界的要求，因此 `Bash(git)` 既可以匹配 `gitleaks`，也能匹配 `git status`。若要强制要求前缀作为一个完整的单词，请包含一个末尾空格以及通配符（如 `Bash(git *)`）。
- **Glob**：模式以 glob 的方式匹配整条命令。`*` 可以出现在任何位置并且匹配任意字符，包括空格和斜杠，所以 `Bash(git * main)` 可以匹配 `git checkout main`。系统同样支持 `?` 以及 `[...]`。

匹配是区分大小写的。在匹配之前会去除命令的前导空白字符；其他方面不会进行规范化。

Bash 规则末尾的 `:*` 后缀会被剥离为一个普通前缀：`Bash(git commit:*)` 变成了前缀 `git commit`。由于前缀没有单词边界，写作 `Bash(sed:*)` 的 `deny` 也会阻止诸如 `sed-custom` 这类命令。

**链式命令。** Codel 会像 Shell 一样解析每条命令，并依据 `&&`, `||`, `;`, `|` 以及换行符对它们进行拆分。规则的操作方式会对不同的片段有不同的处理：

- `deny` 和 `ask` 规则会针对每一个片段以及整个字符串进行检查。只要有一个片段被拒绝，整个命令就会被拒绝。
- `allow` 规则仅针对完整的命令字符串进行检查。因此，`Bash(git *)` 会自动批准 `git status && rm -rf /`，因为完整的字符串是以 `git ` 开头的。请将狭窄的 allow 规则与 `deny` 规则配对使用，以便拦截你想屏蔽的模式。

当配置了 Bash 限制时，无法拆分为简单片段的命令（子 shell、命令替换 `$(...)`、反引号、后台执行 `&`、控制流）将作为一个整体引发提示。

片段级别的检查（`deny` 和 `ask` 规则、被记住的授权以及只读命令列表）会剥离诸如 `RUST_LOG=debug` 这样的环境变量前缀，并剥离一组固定的进程包装器（`timeout`, `nice`, `ionice`, `chrt`, `stdbuf`, `env`），以便 `deny` 和 `ask` 规则能够匹配被包装的或是内部的命令。`deny` 和 `ask` 规则还会检查通过 `-c` 传递给 `bash` 的内联脚本内部。其他的包装器，包括 `sudo`, `xargs` 和 `nohup` 是不会被剥离的；请将它们显式包含在规则编写中。`allow` 规则不包含此项处理：它们会按原本编写的命令字符串进行匹配，因此位于前方的环境变量赋值或者包装器将导致 `allow` 规则无法匹配，并引发命令提示。

### 危险命令

内置的列表（`rm`, `chmod`, `chown`, `chgrp`, `chattr`, `pkill`, `kill`, `killall`, `git push`）即使有某个片段被记住的命令前缀或是只读命令列表所覆盖，它依然会引发提示。配置文件中的显式 `allow` 规则确实能够批准它们，并且总是批准模式会像批准其他命令一样自动批准它们；请使用 `deny` 规则无条件地拦截它们。在将类似 `Bash(rm *)` 的规则作为 allow 规则加入前，请务必仔细检查。

### 读取、编辑与 Grep 规则

路径模式是用工具调用所使用的路径字符串来进行 glob 匹配：

- `*` 和 `?` 不能跨越 `/`；`**` 可以。`Read(src/*)` 能够匹配 `src/main.rs` 但不能匹配 `src/nested/mod.rs`；使用 `Read(src/**)` 可以匹配整个树。
- 单独的文件名仅能精确匹配该字符串。使用 `**/.env` 能够匹配任意深度的 `.env`。
- 没有锚点前缀：模式中前导的 `//` 或 `~/` 会被当作字面量 glob 文本处理。请使用绝对路径模式或是 `**/` 模式。
- 路径是以给定时的状态进行匹配的，而不会被规范化。无论路径是绝对路径还是相对路径，都取决于工具是如何被调用的，因此旨在作为边界的模式应当兼顾这两种形式（例如 `/repo/secrets/**` 以及 `secrets/**`）。
- `Read` 规则还能够约束 `grep` 搜索；`Grep(...)` 规则仅针对 grep 生效。

`Read` 和 `Edit` 的 deny 规则还会额外作用于 shell 命令碰及到的文件路径（例如针对被拒绝路径执行的 `cat` 或 `sed`），这也包括通过 `-c` 传递给 `bash`, `sh`, `dash`, `zsh` 或是 `ksh` 的字面内联脚本；该在 shell 级别的检查也会解析符号链接。但 `read_file`/`search_replace` 工具的直接检查不会解析符号链接。如果要在 OS 级别施加覆盖每个进程的强制要求，请将 deny 规则同沙盒安全环境结合使用（[18-沙盒安全环境.md](18-沙盒安全环境.md)）。

### MCP 规则

`MCPTool(...)` 模式能够全面匹配 `server__tool` 形式下的 Codel 工具名称，并支持 glob 模式：`MCPTool(linear__*)` 会匹配来自 `linear` 服务器的所有工具。Codel 工具名称并不携带 `mcp__` 前缀，因此写为 `mcp__server__tool` 的规则永远不会匹配到某次 MCP 调用；请改为编写 `MCPTool(server__tool)`。

### WebFetch 规则

- `WebFetch(domain:example.com)` 会匹配该主机及其所有的子域名（`api.example.com`），不区分大小写，且忽略前导的 `www.`。在 `domain:` 模式内部是不支持通配符的。
- 不带有 `domain:` 前缀的模式会对完整的 URL 进行 glob 匹配：`WebFetch(https://api.example.com/*)`。

### 工具名称

系统能够识别的工具名称有：`Bash`, `Read` (以及 `NotebookRead`), `Edit` (以及 `Write`, `NotebookEdit`), `Grep` (以及 `Glob`), `MCPTool`, `WebFetch`, `WebSearch`。单独的 `*` 规则能够匹配任意工具。在工具名称的位置上是不支持 glob 模式的。

包含了未被识别的工具（例如 `Agent(model:opus)`）的规则将被跳过并引发警告，而不会导致加载失败。

### 评估顺序

来自各种来源的规则将被合并至单个集合之中，并根据严重性而非顺序进行评估：任何匹配的 `deny` 将执行拒绝；否则任何匹配的 `ask` 将引发提示；否则任何匹配的 `allow` 将予以批准。若没有规则匹配，请求将回落到内置的自动批准，然后遵从提示策略，详见[工具调用如何获得授权](#工具调用如何获得授权)。

## 交互式批准及其持久化位置

当工具调用要求被批准时，权限提示会提供如下选项：

- **允许一次**：针对此次调用予以批准。
- **拒绝一次**：拒绝此次调用，并可选择向模型返回一条消息。
- **启用总是批准模式**：批准所有的后续工具调用，而不局限于当前提示的调用。
- **允许此会话的所有编辑**：在编辑文件时展示。此项授权仅保留在内存中，在重新启动后不会存留。

### 针对命令的“总是允许”

提供了一组更精细的选项，仅能够记住当前正在被提示的具体命令、MCP 工具，或者网络获取域名，例如“总是允许 `cargo test`”。这些选项卡默认是关闭的。启用它们：

```toml
# ~/.codel/config.toml
[ui]
remember_tool_approvals = true
```

在启用此闸门后，提示中会增加：

- **`总是允许: <command>`**，这将会对该命令前缀的允许执行持久化操作。
- 匹配到的“从不允许”行，这会以同样方式对拒绝执行持久化。
- 以及针对 MCP 工具和网络获取域名等同的“总是允许”行。

被记住的前缀仅限于简短形式的命令：只读命令仅对其列出的前缀进行持久化（例如 `git status`，而非整个参数列表），而其他命令则持久化一个简短的起始前缀。在您确认前，提示会准确无误地展示哪些内容将被记住。位于[危险命令](#危险命令)上的命令会再次发起提示，而不会沿用被记住的前缀。

### 持久化是针对每个项目的

交互式授权存放于您 home 目录下的 Codel 的私有状态目录中，作用域限定于启动 Codel 的目录下。在一个项目内生成的授权绝不会被应用于另一个项目，授权内容不会被写入代码仓库，它们亦非为手工编辑而设计。

交互式授权系属个人级、单机级的状态。如果你想将白名单存入代码审查并且与团队成员进行共享，请转而使用项目 `.codel/config.toml` 中的声明式规则。

## 借助 Hook 将 Bash 限定为特定命令

`PreToolUse` 钩子可以针对 `Bash` 工具实施一个在所有权限模式下均适用的白名单。钩子在权限系统之前被评估；由钩子生成的拒绝将终止调用，而钩子生成的允许将交由常规的权限检查处理（如此您的 `deny` 规则依然生效）。

> **注意：** 钩子采取故障开放原则。如果钩子脚本崩溃、超时或是丢失了，系统会当作该工具调用已被钩子允许那样继续进行，并且这一故障将在用户界面中报告。当钩子充当安全边界时，它必须要自行处理自身的错误，且必须把链式命令纳入考量，就像下面的示例那样。请参阅 [10-hooks.md](10-hooks.md)。

### 示例：仅允许 `git` 和 `gh`

**`~/.codel/hooks/git-gh-only.json`**

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "git-gh-only.sh",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

**`~/.codel/hooks/git-gh-only.sh`**

```bash
#!/bin/sh
# 仅允许 git 和 gh 命令，包含链式命令的内部。

set -eu

deny() {
  echo '{"decision": "deny", "reason": "'"$1"'"}'
  exit 2
}

INPUT=$(cat)
CMD=$(echo "$INPUT" | jq -r '.toolInput.command // empty')

[ -n "$CMD" ] || deny "不允许空命令"

# 将 '&&' 和 '||' 规范化为 ';'，以便可以对链条进行片段级别的检查，
# 随后对本脚本无法核查的构造予以拒绝。
CMD=$(echo "$CMD" | sed 's/&&/;/g; s/||/;/g')
case "$CMD" in
  *'$('*|*'`'*|*'&'*|*'>'*|*'<'*) deny "不允许使用替换、后台运行以及重定向功能" ;;
esac

# 以分隔符为界进行分割，并要求每个片段必须以 git 或 gh 作为起始。
echo "$CMD" | tr ';|' '\n\n' | while IFS= read -r SEGMENT; do
  SEGMENT=$(echo "$SEGMENT" | sed 's/^[[:space:]]*//')
  [ -n "$SEGMENT" ] || continue
  case "$SEGMENT" in
    git\ *|git|gh\ *|gh) ;;
    *) deny "仅允许 git 和 gh 命令。被拦截片段: $SEGMENT" ;;
  esac
done
```

```bash
chmod +x ~/.codel/hooks/git-gh-only.sh
```

此钩子能够拒绝所有的 `Bash` 命令，除非每个链式片段皆以 `git` 或是 `gh` 作为起始；并且彻底回绝命令替换、后台处理以及重定向操作，原因在于它无法核实其将要执行的具体内容。在任意权限模式下，该钩子皆能奏效。

若需了解钩子的安装、JSON 格式，以及面向项目钩子及其他事件的信任模型，请参阅 [10-hooks.md](10-hooks.md)，该文档内还囊括了一份作为互补的“拦截危险模式”示例。

## 示例配置

### 无头交互模式下仅使用 git 与 gh (持续集成与自动化)

```bash
codel -p "Implement the feature using only git and GitHub CLI" \
  --allow 'Read' \
  --allow 'Grep' \
  --allow 'Bash(git *)' \
  --allow 'Bash(gh *)'
```

安装上述 `git-gh-only` 钩子来拒绝除此以外的其他一切 `Bash` 命令。若要为所有的工具确立默认拒绝的基调，亦可在 `.claude/settings.json` 内配置 `{"permissions": {"defaultMode": "dontAsk"}}`。

### 只读模式下的代码审查者

```toml
# .codel/config.toml
[permission]
rules = [
  { action = "allow", tool = "read" },
  { action = "allow", tool = "grep" },
  { action = "deny",  tool = "edit" },
  { action = "deny",  tool = "bash" },
]
```

### 交互式开发

在 `default` 模式的辅佐下，针对那些您最为常用的命令（诸如 `git`、`cargo test`、`rg` 等），可运用作用范围较窄的 `Bash(...)` 允许规则。

## 与沙盒安全环境的结合

权限体系关乎模型有资格去请求什么。而操作系统级别的沙盒安全环境（参阅 [18-沙盒安全环境.md](18-沙盒安全环境.md)）则掌控着进程纵使命令已然获批，其最终能够实施何等操作。

对于不受信任代码的推荐组合：

1. `dontAsk` 结合窄作用域的 allow 规则，或是设定约束性钩子
2. `--sandbox strict` 或是某一自定义的配置文件
3. 建立项目信任并且审查各种 `SessionStart` 钩子

## 在 TUI 中管理权限

- 权限的裁定会呈现在对话记录（transcript）中。
- `/always-approve` 命令专司切换总是批准模式；其他模式则需通过 `defaultMode` 予以设置（详见 [设置模式](#设置模式)）。
- 当配置了 `[ui] remember_tool_approvals = true` 时，权限提示符将把仅针对当下项目产生持久效力的面向命令级别的“总是允许”选项囊括在内。参见 [交互式批准及其持久化位置](#交互式批准及其持久化位置)。
- 如若管理钩子及插件，敬请执行 `/hooks` 或是 `/plugins`（在大部分终端上，**Ctrl+L** 亦能启开扩展界面的模态框；而在 VS Code、Cursor、Windsurf 与 Zed 中，`Ctrl+L` 意指插入拦截操作）。参见 [10-hooks.md](10-hooks.md)。

## 最佳实践

1. **更倾向于使用范围狭窄的模式。** 相比于裸露的 `Bash` 允许规则，`Bash(git *)` 所赋予的权限更小。
2. **结合各个层级。** `dontAsk`、窄 allow 规则、限制性的钩子以及沙盒安全环境皆在各自独立地施加限制。
3. **针对未知来源核查项目配置。** `.codel/config.toml` 以及 `.claude/settings.json` 中包括 `allow` 规则在内的项目权限规则，在无需经由独立信任提示的情况下即行生效。在陌生的项目中运作之前，敬请审查它们以及形形色色的项目钩子（详见 [10-hooks.md](10-hooks.md) 里的安全提示）。
4. **对你的策略加以测试。** 伴随着 `defaultMode: "dontAsk"` 的设立（或是完成 `PreToolUse` 钩子的安装），请执行具有代表性的命令，以此核实究竟有哪些行径遭到了拦阻。
5. **将只读命令列表视作一项便捷举措，而绝非充当安全边界。**
