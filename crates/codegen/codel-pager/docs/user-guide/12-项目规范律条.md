# 项目规范律条 (AGENTS.md)

项目规范律条允许你在每个项目或每个目录下单独配置 Codel。通过在仓库中放置一个 AGENTS.md 文件，你可以指定代码规范、构建指令、编码风格指南以及 Codel 在该代码库中工作时需要遵循的任何其他指令。

---

## 什么是项目规范律条？

项目规范律条是 Codel 读取并添加到其上下文中的 Markdown 文件。Codel 在该目录树中的每次交互均会遵循其中的内容。

这是向 Codel 传授项目规范的首要机制，因此你无需在每个会话中重复解释它们。

---

## 支持的文件名

Codel 会在每个目录下按照以下顺序检查这些文件名：

- `Agents.md`
- `Claude.md`
- `CLAUDE.md`
- `CLAUDE.local.md`
- `AGENT.md`
- `AGENTS.md`

Codel 会加载某个目录中所有匹配的文件，因此一个同时包含 `AGENTS.md` 和 `CLAUDE.md` 的文件夹会同时包含这两个文件的内容。在不区分大小写的文件系统上，解析为同一文件的名称（如 `Agents.md` 和 `AGENTS.md`）会被去重并仅统计一次。`Claude.md`、`CLAUDE.md` 和 `CLAUDE.local.md` 被支持用于兼容 Claude Code 工作流。当开启 Claude 兼容性时（默认开启），Codel 还会扫描你主目录级别的 `~/.claude/` 目录寻找这些文件名，并在每个目录层级检查 `.claude/CLAUDE.md` 和 `.claude/CLAUDE.local.md` -- 即 Claude Code 用于项目记忆的存储位置。在开启 Cursor 兼容性时，主目录级别的 `~/.cursor/` 目录也会以相同方式被扫描。

### 规则规范目录

除了 AGENTS.md 文件之外，Codel 还会扫描从仓库根目录到当前工作目录的每一个层级（`<dir>`）中 rules 规则目录下的 `*.md` 文件：

| 位置 | 说明 |
|----------|-------|
| `<dir>/.codel/rules/` | 始终扫描 |
| `<dir>/.claude/rules/` | Claude 兼容性（可配置） |
| `<dir>/.cursor/rules/` | Cursor 兼容性（可配置） |

无论从何处启动，Codel 也会扫描主目录级别的规则规范。这些根目录已经具备厂商特定性，因此规则规范直接存放在 `rules/` 下：

| 位置 | 说明 |
|----------|-------|
| `$CODEL_HOME/rules/` (默认 `~/.codel/rules/`) | 始终扫描；适用于所有项目 |
| `~/.claude/rules/` | 由 `compat.claude.rules` 控制 |
| `~/.cursor/rules/` | 由 `compat.cursor.rules` 控制 |

主目录规则最先加载（按表格顺序），随后是按从仓库根目录到当前目录顺序加载的项目文件。在每个 rules 目录内部，文件按字母顺序排列。厂商 `rules` 单元格控制主目录和项目规则，独立于对应的 `agents` 单元格。Claude 的 `agents` 单元格管控 `~/.claude/` 下的命名文件和项目 `<dir>/.claude/CLAUDE*.md`；通用的顶层名称如 `Claude.md`、`CLAUDE.md` 和 `CLAUDE.local.md` 始终保持被识别。参阅[系统配置](05-系统配置.md#harness-工具链兼容性)。

## 自动发现机制

Codel 按以下顺序扫描项目规范律条：

1. **主目录规则**：`$CODEL_HOME`，而后是已启用的 `~/.claude/` 与 `~/.cursor/` 来源
2. **仓库规则**：如果在 git 仓库内部，从仓库根目录向下直达当前工作目录（含）的每一个目录
3. **仅限当前目录 (CWD-only)**：如果不在 git 仓库内部，仅扫描当前工作目录

### 示例

对于以下项目结构：

```
~/projects/my-app/
  AGENTS.md              # "Use TypeScript. Follow ESLint rules."
  src/
    AGENTS.md            # "Prefer functional components."
    components/
      AGENTS.md          # "Use CSS modules for styling."
```

当 Codel 在 `~/projects/my-app/src/components/` 中运行时，它会加载所有这三个文件。这些指令是累加的，因此 Codel 会同时看到它们所有内容。

### 层级越深的文件优先级越高

Codel 会将文件从仓库根目录到当前工作目录进行排序，因此在较深目录中的文件会出现在其上下文的较后位置，并在指令发生冲突时享有更高优先级。在上面的示例中，如果根目录说“使用 styled-components”，但 `components/AGENTS.md` 说“使用 CSS modules”，由于 CSS modules 的指令出现在后面，它将胜出。

### 自动加载行为

- 在会话启动时，Codel 会自动加载从仓库根目录到当前工作目录的文件。
- 当 Codel 在初始集合之外的目录中读取、列出或编辑文件时，它会检测那里的任何项目指令文件，记录其路径，并在适用于任务时读取它们。

## 项目规范律条中应该包含什么

### 编码规范

```markdown
# 编码规范

- 所有新代码均使用 TypeScript
- 优先使用带 Hooks 的函数式组件，而非类组件
- 默认使用 `const`；仅在需要重新赋值时使用 `let`
- 最大行长：100 个字符
```

### 构建与测试指令

```markdown
# 构建与测试

- 在提交前运行 `npm test`
- 使用 `npm run lint` 检查代码风格
- 使用 `npm run build` 进行构建 -- 确保没有 TypeScript 错误
- 集成测试：`npm run test:e2e`（需要 Docker）
```

### 样式与代码风格指南

```markdown
# 代码风格指南

- 遵循 Airbnb JavaScript 风格指南
- 使用 2 个空格缩进
- 多行数组/对象中始终使用尾随逗号
- 优先使用模板字面量而非字符串拼接
```

### PR 与 Commit 提交要求

```markdown
# 版本控制

- 使用规范提交 (conventional commits) 格式编写提交信息
- 分支名称前缀为 `feature/`、`fix/` 或 `chore/`
- 所有 PR 在合并前必须获得至少一次批准
- 变基/压缩合并 (Squash-merge) 特性分支
```

### 架构说明

```markdown
# 架构规范

- API 路由保存在 `src/routes/` 下，每个资源一个文件
- 业务逻辑保存在 `src/services/` 下
- 数据库查询保存在 `src/repositories/` 下
- 绝不要在 `src/services/` 中从 `src/routes/` 导入内容
```

## 将规则限制在子目录作用域

AGENTS.md 文件将其作用域限定在该文件夹为根的整个目录树中。利用这一点可以为代码库的不同部分提供不同的指令：

```
my-monorepo/
  AGENTS.md                    # 整个 Monorepo 范围的规则
  packages/
    frontend/
      AGENTS.md                # "Use React. Prefer CSS modules."
    backend/
      AGENTS.md                # "Use Express. Follow REST conventions."
    shared/
      AGENTS.md                # "No framework-specific code in this package."
```

## 会话级别的规则标志

为了在不修改文件的情况下为单个会话添加规则，请传入 `--rules`（别名 `--append-system-prompt`）：

```bash
codel --rules "Always use TypeScript. Prefer functional components."
```

Codel 会将此文本附加到会话的系统 Prompt 末尾。可将其用于会话特定的定制。

若想彻底替换系统 Prompt，请传入 `--system-prompt-override`（别名 `--system-prompt`）。Codel 将原样使用该文本，并跳过默认的系统 Prompt 和 `--rules`。（相比之下，使用 `--rules` 传递的文本会被包裹在 `<human_rules>` 块中并附加到默认 Prompt 之后。）

## 文件大小

Codel 会完整加载每个项目指令文件；没有字符上限也没有截断。即便如此，也请保持指令精简且专注。比起冗长的规则，较短且具体的规则更容易被 Codel 遵循，并且你加载的每个文件都会消耗上下文。

---

## Gitignore 过滤规则

在发现过程中，被 `.gitignore` 忽略的文件会被跳过。为了避免将个人覆盖设置存入共享仓库，可以将被识别的文件名（如 `CLAUDE.local.md`）加入 gitignore：

```gitignore
# .gitignore
CLAUDE.local.md
```

作为顶层指令文件，Codel 仅会发现[支持的文件名](#支持的文件名)中列出的已知文件名 -- 而非诸如 `AGENTS.local.md` 或 `notes.md` 等自定义名称。（在诸如 `.codel/rules/` 的规则目录下，每个 `*.md` 文件无论名称为何都会被加载。）

## .codel/ 项目目录

除了 AGENTS.md 文件外，项目根目录下的 `.codel/` 目录还可以包含额外的项目级配置：

| 路径 | 用途 |
|------|---------|
| `.codel/config.toml` | 项目级作用域的 MCP 服务器、插件和权限规则（其他设置仅从 `~/.codel/config.toml` 加载） |
| `.codel/skills/` | 项目级作用域的技能扩展定义 |
| `.codel/plugins/` | 项目级作用域的插件 |
| `.codel/agents/` | 项目级作用域的 Agent 定义 |
| `.codel/hooks/` | 项目级作用域的生命周期钩子 |
| `.codel/lsp.json` | LSP 服务器配置 |

这些均为可选配置。详情请参阅各自对应的指南。

## 检查已加载的规则

使用 `codel inspect` 查看所有已加载的项目指令：

```bash
codel inspect
```

这会显示它找到的每个项目指令文件，连同其路径和大约的 Token 数量。使用该命令可以确认 Codel 是否正确读取了你的规则。

## 最佳实践

1. **从根目录开始。** 将最重要的、项目通用的规则放在仓库根目录的 AGENTS.md 中。

2. **描述要具体。** “使用 TypeScript” 比 “使用现代 JavaScript” 更好。“提交前运行 `cargo fmt`” 比 “格式化你的代码” 更好。

3. **保持精简。** 相比冗长的指令，精简的指令更容易被遵循。

4. **对大型仓库使用子目录作用域。** Monorepo 的不同部分可能有不同的规范。使用按目录划分的 AGENTS.md 将规则合理限制在对应作用域。

5. **对你的规则进行版本控制。** 将 AGENTS.md 提交到仓库中，以便整个团队受益。特定用户的覆盖设置属于 `~/.codel/`（全局规则）。

6. **不要重复文档内容。** AGENTS.md 应该包含可落地的操作指令，而非项目 README 的复刻。必要时请链接到外部文档。

7. **期审查。** 随着项目的演进，及时更新你的规则以匹配当前的最新规范。
