# 筹划模式 (Plan Mode)

筹划模式是一个结构化的规划阶段：在编写任何代码之前，智使 (Agent) 会探索代码库并设计实现方案。当任务的正确方法确实存在歧义时，请使用它，在编码之前获得您的输入可以避免大量返工。

---

## 筹划模式的作用

当筹划模式处于活动状态时，智使：

1. 阅读并搜索代码库以理解现有的模式和架构
2. 设计一个实现方案并将其写入筹划文件 (plan file)
3. 可能会使用 `ask_user_question` 来澄清具体问题
4. 调用 `exit_plan_mode` 提交方案供您审批

除了筹划文件外，筹划模式是只读的：筹划文件（会话目录中的 `plan.md`）的编辑会自动批准，而对任何其他文件的编辑会被直接拒绝——工具调用会失败，并返回一条简短消息，指出筹划文件是唯一可编辑的路径。这在所有权限模式下都成立，包括“始终批准” (always-approve)。将规划与实现分离让您能够在编写任何代码之前审查和纠正方案。

---

## 如何进入筹划模式

### 智使主动进入

当智使判定任务存在真正的歧义时，它会进入筹划模式。它会调用 `enter_plan_mode` 工具，这需要您的批准才能激活筹划模式。如果您拒绝，智使将保持在正常模式。

**适合触发筹划模式的场景：**

- “为应用添加用户认证” —— 确实存在歧义（会话 vs JWT、令牌存储、中间件结构）
- “重新设计数据流水线” —— 重大的架构调整，错误的方法会浪费大量精力
- “为 API 添加缓存” —— 有多种合理的方法（Redis vs 内存 vs 基于文件）
- “添加实时更新” —— 架构决策（WebSockets vs SSE vs 轮询）

**不适合筹划模式的场景：**

- “在用户资料中添加一个删除按钮” —— 实现路径清晰
- “修复 README 中的错别字” —— 直接明了
- “更新 API 中的错误处理” —— 直接开始工作，需要时再问具体问题
- “我们可以开始做搜索功能吗？” —— 用户希望直接开始，而不是计划

### 用户主动进入

您可以通过两种方式自己进入筹划模式：

- **`/plan`** —— 进入筹划模式。当您发送下一个提示词时，筹划模式将激活。运行 `/plan <描述>` 可在一步内进入筹划模式并以该描述开始交互。
- **Shift+Tab** —— 循环切换会话模式：正常，然后是筹划，接着是始终批准，最后回到正常。从正常模式按一次即可切换到筹划模式。

当筹划文件存在后，运行 **`/view-plan`**（别名 `/show-plan`, `/plan-view`）以重新打开其保存的预览。

## 筹划文件

筹划方案会写入会话目录内的 `plan.md`（`~/.codel/sessions/<cwd>/<session-id>/plan.md`，其中 `<cwd>` 是编码后的目录名，并非字面路径）。

筹划文件包含：

- 一个**上下文**部分，解释进行此更改的原因
- 推荐的方法（不是列出每个备选方案）
- 需要修改的关键文件路径
- 可重用的现有函数和实用程序，及其文件路径
- 一个验证部分，描述如何端到端地测试这些更改

---

## 筹划方案审批

当智使完成规划后，它会调用 `exit_plan_mode` 工具。该工具从磁盘读取筹划文件，TUI 会打开一个可滚动的方案预览，底部带有操作栏。

如果智使退出时未编写方案（`plan.md` 为空或缺失），同一个审批界面仍会打开，并显示清晰的空状态消息，以便您可以批准并开始实现、请求修改（将智使送回规划阶段）或退出。在极简模式下，空状态通知会提交到回滚缓冲区中，控制栏标题显示为 **未编写任何计划**。

### 审查筹划方案

使用方向键或 `j`/`k` 滚动方案。操作栏显示以下快捷键：

| 快捷键 | 操作                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------- |
| `a`      | 批准方案并开始构建。如果有待处理的评论，此处将显示 `approve w/ comments` 并将评论与批准一起发送。 |
| `s`      | 请求修改。焦点移动到提示框，以便您输入修订意见；按 `Enter` 发送。 |
| `c`      | 对选定的行或行范围进行评论。                                                          |
| `q`      | 退出筹划 —— 放弃方案，不批准并关闭筹划模式。                              |

按 `Tab` 键在方案预览和提示框之间移动焦点。

### 提供反馈

审批视图具有三种焦点状态：

- **预览 (Preview)**: 滚动方案并选择要评论的行。
- **评论 (Commenting)**: 在所选行范围内添加内联评论（按 `c`，或在某行上按 `Enter`）。
- **提示 (Prompt)**: 输入自由格式的修订意见。

按 `Tab` 键在预览和提示框之间切换。当您发送反馈——内联评论、自由格式的意见或两者兼有——智使会收到它并修改方案。筹划模式将保持活动状态，以便您可以进行迭代。

### 离开审批视图

按 `Esc` 键将焦点从提示框返回到方案预览。要关闭审批而不批准或发送反馈，按 `q` 退出筹划。退出操作会放弃拟议的方案并关闭筹划模式。

## 筹划模式生命周期

筹划模式状态机有四个状态：

| 状态          | 描述                                                    |
| -------------- | -------------------------------------------------------------- |
| `Inactive`     | 正常运行模式。无筹划模式约束。               |
| `Pending`      | 客户端已开启筹划模式，但尚未发送任何提示词。  |
| `Active`       | 筹划模式活动中。对筹划文件的编辑会自动批准；对其他文件的编辑会被拒绝。 |
| `ExitPending`  | 当一次交互正在进行时，用户关闭了筹划模式。          |

转换关系：

```
Inactive    --> Active   (调用并批准了 enter_plan_mode 工具 —— 跳过 Pending)
Inactive    --> Pending  (您通过 /plan 或 Shift+Tab 开启了筹划模式)
Pending     --> Active   (您的第一个提示词激活了筹划模式)
Active      --> Inactive (exit_plan_mode 被批准，或您在空闲时关闭了筹划模式)
Active      --> ExitPending (您在交互进行中关闭了筹划模式)
ExitPending --> Inactive (交互完成后)
```

筹划模式状态被持久化到磁盘中并在进程重启后保留。瞬态 (`Pending`, `ExitPending`) 在重启时折叠为 `Inactive`，因为它们依赖于进行中的交互。

## 筹划模式期间的编辑

在筹划模式活动期间，对筹划文件的编辑无需提示即会自动批准，因此智使可以自由地迭代方案。对 **任何其他文件的编辑均会被拒绝** 并在运行前拦截——智使会收到一条简短消息，指出筹划文件是唯一可编辑的路径。

这种强制执行独立于权限模式：

- **“始终批准” (always-approve / yolo) 在筹划模式下保持待命。** 非编辑工具（bash 命令、读取操作、MCP 工具）仍然自动运行，但文件编辑将被阻止，直到您批准退出筹划模式。一旦方案获批，始终批准模式将恢复以进行实现。
- 不会检查 Bash 命令的文件写入——筹划模式阻止的是编辑工具，而不是 Shell 重定向。
- 分身智使 (Subagent) 不受父会话筹划模式编辑关卡的限制。每个分身智使 (Subagent) 启动时带有全新的筹划模式追踪器 (`Inactive`)，因此一个具有写入能力的 `general-purpose` 或其他类型的分身智使可以在父会话处于筹划模式时编辑文件——而且它会继承父级的权限模式（包括始终批准）。像 `explore` 这样的只读类型则依然受限于其自身的工具集。

状态标志在筹划模式激活时显示 `plan`。如果底层开启了始终批准，当筹划模式退出时，其标志会重新出现。

---

## 筹划模式与上下文压缩

当 `/compact` 在活跃的筹划模式会话中运行时，筹划模式的状态会被保留。压缩后的上下文中包含筹划模式处于激活状态的提醒，因此智使在压缩后将继续规划。

---

## 何时适用筹划模式

**请在以下情况使用筹划模式：**

- 具有明显架构歧义（多种合理方案）的任务
- 需要在实施前进行探索的不明确需求
- 错误方法会浪费大量精力的高影响度重构

**以下情况请跳过筹划模式：**

- 具有清晰实施路径的任务
- 只要理解错误原因即可明确修复方案的错误修复
- 遵循现有约定的功能添加
- 直接简单的修改（重命名、格式化、添加测试）
- 研究和探索任务（请改用分身智使）
