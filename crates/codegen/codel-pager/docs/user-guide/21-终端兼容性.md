# 终端兼容性与故障排除 (Terminal Support and Troubleshooting)

Codel Build 作为全屏 TUI 运行。它依赖终端对颜色、剪贴板、键盘输入、鼠标输入和全屏显示的支持。不同的终端、多路复用器 (multiplexers)、容器和 SSH 会话在处理这些功能时可能会有所不同。

## 诊断和修复终端问题

在 Codel 中运行 `/doctor` 以检查当前会话并查看可用的修复方法。如果 Codel 无法启动，请在您的 shell 中运行 `codel doctor`。使用 `codel doctor --json` 可获取机器可读的报告。

Doctor 会检查终端、多路复用器、颜色支持、键盘和换行行为、剪贴板路由，以及（包含音频捕获时）麦克风的可用性。应用内命令还能检查实时的会话详细信息，例如通知焦点跟踪和沙盒安全环境配置文件的冲突情况。

报告可能包含问题或建议，但仍会成功退出。当通过管道传输时，`codel doctor --json` 会报告相同的颜色功能。麦克风检查不会开始录音，因此 Doctor 无法探测到在捕获期间仅表现为静音的 macOS 权限故障。

`/terminal-setup`、`/terminal-check` 和 `/terminal-info` 仍然是 `/doctor` 的别名。

当 Doctor 发现了一个明确的 tmux 不良设置时，`/doctor fix` 会列出可用的自动修复方案。一次应用一个指定的修复，例如 `/doctor fix tmux-clipboard` 或 `codel doctor fix dcs-passthrough --yes`。
Doctor 可以持久化以下三个 tmux 选项：

- `terminal.tmux-clipboard` — `set -g set-clipboard on`
- `terminal.dcs-passthrough` — `set -wg allow-passthrough on`
- `terminal.tmux-extended-keys` — `set -g extended-keys on`

tmux 修复仅会编辑托管受影响 tmux 服务器的计算机上的持久配置文件，包括远程会话。普通 tmux 使用真实的 `$HOME/.tmux.conf`；Byobu-tmux 使用其生效的 `BYOBU_CONFIG_DIR`，如果该目录不可用或不安全，则会拒绝猜测。Codel 会保留文件的行尾和权限模式，在更改现有文件时进行备份，并拒绝冲突的或模棱两可的直接赋值。

Codel 故意**不**运行 `tmux source-file` 或更改正在运行的 tmux 服务器。在应用修复后，使用显示的精确命令重新加载，或者分离并重新附加，然后再次运行 `/doctor`。在重新加载之前，预计还会保留实时的发现结果。保守的配置扫描仅检查全局的直接分配；您自己应负责检查来源文件 (sourced files)、条件语句、插件和生成的 tmux 设置。

## 检测到的终端

Codel 会根据环境变量检测这些终端模拟器：

- **Apple Terminal**
- **Ghostty**
- **iTerm2**
- **Warp**
- **WezTerm**
- **Kitty**
- **Alacritty**
- **Rio**
- **foot** (Wayland 原生，Linux)
- **VS Code**、**Cursor**、**Windsurf** 和 **Zed** 集成终端
- **JetBrains** IDE 终端
- **Codel Desktop**
- 基于 **VTE** 的终端，如 GNOME Terminal、GNOME Console 和 Tilix
- **Windows Terminal**

这种检测存在以下限制：

- 在 tmux 内部，标识外部终端的变量可能无法传递给 Codel。
- 在 SSH 上，许多终端变量未被转发。
- tmux 的全局环境反映的是连接到服务器的第一个客户端，而不一定是当前的终端。

## 常见问题及修复

### 颜色看起来不对或缺少真色彩 (truecolor)

运行 `/doctor`。获得完全支持的设置应显示 `color truecolor` 和 `themes all`。如果没有，Doctor 将显示探测到的限制以及相应的修复方法。

### 剪贴板问题

Codel 通过最多三个路由来执行写入，它们在 `/doctor` 的 **Clipboard** (剪贴板) 选项下显示：

- **native** — 本地操作系统的剪贴板。
- **tmux** — 当 Codel 在 tmux 内部运行时使用的 tmux 粘贴缓冲区。
- **OSC 52** — 一种可以跨越 tmux、容器或 SSH 传递的转义序列。

#### Wayland

现代 Wayland 合成器 (compositors) 无需保持终端处于焦点即可更新剪贴板。较旧的合成器可能需要 Codel 保持焦点状态，直到出现复制消息。当存在这种情况时，Codel 会在启动时显示警告；运行 `/doctor` 可获取探测到的状态和步骤。

`CODEL_CLIPBOARD_NO_DATA_CONTROL=1` 是一个高级的后备选项，它会禁用数据控制路由。开启后将使用命令行剪贴板工具来进行复制。

#### OSC 52 关闭开关 (kill switch)

当在 Linux 下以及通过 tmux、SSH 或无显示的容器启用了相关路由时，Codel 会发出 OSC 52。不支持 OSC 52 的终端可能会将编码的有效载荷显示为纯文本。在启动 Codel 之前设置 `CODEL_CLIPBOARD_NO_OSC52=1` 以禁用该路由。这会导致 `/doctor` 显示 `osc 52 off`；native 和 tmux 路由不受影响。

#### Linux X11 选区

X11 中的 **PRIMARY** 和 **CLIPBOARD** 是分开的：

- 只有设置了 `DISPLAY` 时，未修改的中键单击才会读取 PRIMARY。在 XWayland 下，必须在 `PATH` 中安装 `xclip` 或 `xsel`。
- `Ctrl+V` 将读取 CLIPBOARD，且绝不会回退到 PRIMARY。
- `Shift+Insert` 保留为终端的所选文本粘贴键。

#### SSH 与所选文本

远端的 Codel 进程通常无法读取本地终端的选中内容。请使用终端原生的 `Shift+Insert`，或者当终端需要避开鼠标上报 (mouse reporting) 时，按住 `Shift` 的同时中键单击。

当 Codel 无法在 SSH 上识别外部终端时，它会预测发送 OSC 52，但会将该路由标记为未验证。复制消息会显示实际结果以及备份文件。运行 `/doctor` 以查看其他复制选项。

#### SSH 上的 Apple Terminal

Apple Terminal 不支持 OSC 52，因此远程复制无法直接到达本地剪贴板。Codel 还会将每次复制保存到复制消息中指定的备份文件中（默认为 `~/.codel/last-copy.txt`；可通过 `CODEL_COPY_FILE` 覆盖）。您还可以使用 `/copy <file>` 或 `/minimal`。

要进行直接剪贴板转发，请通过本地计算机的 `codel wrap` 运行 SSH 命令，例如 `codel wrap ssh user@host`。该命令也可用于包装容器和 pod shells。它还会在连接断开后恢复终端模式。

当 SSH 会话未使用 `codel wrap` 时，Codel 将显示一次性提示：“Run `/doctor` for details and fixes.”（运行 /doctor 以了解详细信息并修复）。通过 wrap 启动会话后，该提示将不再出现。您可以在 `/settings` → **Show contextual hints** → **SSH wrap** 中关闭它，或在 `$CODEL_HOME/config.toml` 下的 `[ui.contextual_hints]` 中设置 `ssh_wrap = false`。此设置不会隐藏 Doctor 的建议。

如果是重复使用 SSH，Doctor 会提供 `codel doctor fix ssh-wrap` 修复建议。它还会显示单次运行的命令、将被修改的文件，以及应该绕过别名的情况。标识 `terminal.ssh-wrap` 仍被接受并会出现在 JSON 结果中。

> **警告**：`codel wrap` 处于实验阶段，可能无法在所有设置下正常工作。

#### iTerm2

iTerm2 可能需要授予 OSC 52 剪贴板的访问权限。运行 `/doctor`；其中的 `terminal.iterm2-clipboard-permission` 建议会显示需检查的设置。

### 无法激活全屏或备用屏幕 (alternate screen)

Zellij 和 tmux 的控制模式可能会限制备用屏幕。在这些环境下，Codel 通常使用内联模式。运行 `/doctor` 可查看检测到的情况。
您可以在 `~/.codel/pager.toml` 中配置 `[terminal] alt_screen`，或运行 `codel --no-alt-screen` 以确认内联模式是否有效。

### Zellij 快捷键与 Codel 冲突

Zellij 可能会在 Ctrl/Alt 键到达 Codel 之前进行拦截。在 Zellij 0.41 或更高版本上，请使用 **Unlock-First (non-colliding)** 预设：

1. 按 `Ctrl+o`，然后按 `c`。
2. 打开 **Change Mode Behavior**。
3. 选择 **Unlock-First (non-colliding)**。
4. 按 `Enter` 键应用它。

当您需要使用 Zellij 自身的窗格或会话控制时，请按 `Ctrl+g`。在极简模式下，如果 `Ctrl+G` 依然无法到达 Codel，请打开命令面板并选择 **Edit Prompt in External Editor**（在外部编辑器中编辑提示）。这会保留当前草稿；如果直接输入 `/edit-prompt`，由于该命令本身占据了编写器，因此将启动一个空的编辑器草稿。

### 在 WezTerm 中 Ctrl+Enter 无法换行插话 (interject)

WezTerm 默认禁用 Kitty 键盘协议。在 Codel 中运行 `/doctor`。其 `terminal.wezterm-kitty` 发现项将显示设置和重启步骤。在 SSH 上，Doctor 仅显示当前会话中起效的解决方法。Apple Terminal 使用 `Ctrl+O` 来换行插话，因为它无法识别带有修饰键的 Enter 组合键。

### 在 VS Code 中 Shift+Enter 无法插入换行

VS Code、Cursor、Windsurf 和 Zed 的终端使用了 xterm.js，该工具仅部分实现了 Kitty 键盘协议，并且错误编码了一些带 Shift 的可打印按键。因此，Codel 在这些环境中不会协商该协议，导致 Shift+Enter 到达时与普通的 Enter (`CR`) 相同。这也会影响到当未转发 `TERM_PROGRAM` 时通过 SSH 访问的 VS Code。此时请使用 `Alt+Enter` 来插入换行；`/doctor` 会报告 `terminal.newline-fallback` 并附上检测到的解释和解决方法。

### 鼠标滚动失效

如果 Codel 不再接收鼠标输入，请在终端中重新启用鼠标上报：

- **Apple Terminal**: **View → Allow Mouse Reporting** (`Cmd+R`).
- **iTerm2**: **Settings → Profiles → Terminal → Enable mouse reporting**.

### 语音听写录不到声音

在约 10 秒钟没有听写文本之后，Codel 会停止捕获并显示 **“No speech was detected. Voice stopped.”**（未检测到语音。语音已停止），并提供麦克风的修复步骤。在 macOS 上，被拒绝的麦克风授权在使用时表现与完全静音相同，因为权限归属于托管 Codel 的终端所有。请打开 **系统设置 → 隐私与安全性 → 麦克风**，为终端开启授权并重启它。如果访问权限已开启，请检查 **系统设置 → 声音 → 输入** 下的输入设备和音量级别并重试。

运行 `codel doctor`，或者在开启语音模式的同时运行 `/doctor`。**Voice** (语音) 部分将显示 Codel 会使用的麦克风。如果没有可用的输入设备，Doctor 将显示 `voice.no-input-device` 及其后续步骤。当 macOS 主动提供静音数据时，Doctor 无法被动地检测到 macOS 的麦克风权限被拒。

在 macOS 上，每次听写均使用一个生命周期较短的捕获辅助进程，以便在捕获结束时释放音频栈的内存。如果辅助进程本身可能存在问题，请设置 `CODEL_VOICE_CAPTURE=inprocess` 以使用进程内的后备方案来进行对比测试。

### 带有 GNU screen 的 Byobu

在使用 GNU screen 作为后端的 Byobu 支持有限。`/doctor` 会报告 `terminal.byobu-screen` 并解释如何切换至 Byobu 的 tmux 后端。
